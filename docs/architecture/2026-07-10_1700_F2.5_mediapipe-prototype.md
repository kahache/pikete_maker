# F2.5 — MediaPipe Selfie Multiclass prototype (spike)

Date: 2026-07-10 · Phase 2.5 · Author role: ML Engineer
Status: **prototype spike with real numbers on the 31 CEO selfies.** Follows the
segmentation benchmark (`2026-07-10_1500_F2.5_segmentation-benchmark.md`) and
executes D21 (MediaPipe = confirmed on-device v1, top/bottom only, no footwear)
and D22 (latency non-blocking, ad covers it).

TL;DR: **GO on MediaPipe as the on-device v1.** 16.37 MB model, 0.43 s/image on
laptop CPU, per-garment top/bottom palettes come out correctly on real mirror
selfies, and — the headline — MediaPipe's **skin class retires the crude YCbCr
skin filter**: YCbCr would have mis-flagged **99.2 % of selfie04's burgundy top
as skin**; MediaPipe keeps it in the clothes class.

## 1. Setup (and a sandbox caveat that matters for reproduction)

- Isolated deps: mediapipe **0.10.35** installed via `pip install --target` into
  `scratchpad/mp-libs` (NOT the project `.venv`). Verified post-run: `.venv`
  still has numpy 2.4.6 / cv2 5.0.0 and **no mediapipe** — colorlab is untouched.
- `opencv-contrib-python` (pulled by mediapipe) needs `libGL.so.1` → removed from
  the target dir; mediapipe falls back to `.venv`'s headless-capable cv2 5.0.0.
- **Native runtime vs headless sandbox:** mediapipe 0.10.35's C runtime
  (`libmediapipe.so`) is linked `-z now` against `libGLESv2.so.2` + `libEGL.so.1`,
  which are **absent on this headless box and not installable (no sudo/gcc)**. To
  get real numbers I built **no-op stub `.so`s** exporting the 106 missing GL/EGL
  symbols (assembled with `as`, linked with `ld`) on `LD_LIBRARY_PATH`. CPU
  inference never calls GL, so the stubs are inert and the segmentation output is
  genuine (the sensible masks/palettes below confirm the model really ran).
  **Implication:** this is a *this-machine* constraint, not a MediaPipe one — on
  an Android device (the actual target, D2/D21) MediaPipe ships its own GPU/CPU
  delegates and this problem does not exist. On a normal Linux dev box, `apt
  install libgles2 libegl1` fixes it. Reproduction command in §6.

## 3. Segmentation classes and the top/bottom split

The model emits 6 classes: `background / hair / body-skin / face-skin / clothes /
others(accessories)`. It gives **one "clothes" blob** — no native top/bottom.

**Split used:** vertical cut at the **mid-height of the clothes-region bounding
box** (rows where clothes pixels exist define [r0,r1]; upper = rows < mid, lower
= rows ≥ mid). No Pose model — a pure geometric heuristic. It is crude (the real
waistline is not exactly the bbox midpoint), but it is enough to prove the value
and is trivially on-device. Refinement with MediaPipe Pose hip landmarks is the
obvious v1.1. Clothes coverage fired > 1 % on **35/35** samples (mean 25.1 %),
i.e. the person's garments are reliably found on every mirror selfie — a much
better hit rate than rembg cloth_seg's lower-body class (fired on ~2/12 web
photos in the prior spike).

## 4. PROOF #1 — per-garment palettes on the real selfies

Each region's pixels fed into colorlab `dominant_colors` + `pick_harmony_base`
(imported via `PYTHONPATH=cv_core/src`, **not modified**). Base hex per region,
31 selfies + 4 g0. Honest reading: the hex differs on 35/35, but the *dataset is
deliberately neutral/monochrome outfits*, so on a black or all-beige outfit
upper≈lower is the **correct** answer. The meaningful proof is the genuinely
two-tone outfits, where the split recovers distinct garment colors:

| Selfie | UPPER base | LOWER base | Reading |
|---|---|---|---|
| selfie17 | `#232324` (near-black top) | `#988C80` (tan/beige bottom) | **distinct garments recovered** |
| selfie18 | `#BBB1A6` (light beige top) | `#1B1A1E` (black bottom) | **distinct** |
| selfie19 | `#D7D1CE` (near-white top) | `#232327` (black bottom) | **distinct** |
| selfie08 | `#989FA5` (grey) | `#6C91A3` (blue) | distinct |
| selfie26 | `#325582` (dark denim) | `#6493C5` (lighter denim) | distinct shades |
| selfie27 | `#3A332E` (dark brown) | `#69625F` (taupe) | distinct |
| selfie03 | `#222328` | `#1D1C20` | both near-black → correct (monochrome outfit) |
| selfie04 | `#3E151C` | `#4B1B22` | both burgundy → correct (monochrome outfit) |

Contrast with the whole-photo baseline (from the prior spike): on such outfits
the single-palette pipeline averages garment + background into a muddy neutral.
Per-garment segmentation puts the palette **on the actual garments** and, where
top and bottom differ, returns two real colors. The differentiator holds on the
real MVP dataset.

## 5. PROOF #2 — the skin-class win (retires the YCbCr proxy)

The app's current crude skin filter is a YCbCr box (Cr∈[133,173], Cb∈[77,127]) —
this is what false-flagged selfie04's burgundy top as skin. I applied that exact
box to the **clothes pixels** of each selfie and measured how many it would
**wrongly call skin**. MediaPipe assigns those same pixels to the clothes class.

- **Mean 17.9 % of clothes pixels would be mis-flagged as skin by YCbCr; MediaPipe
  keeps them as clothes.** Worst offenders are exactly the warm-toned garments:

| Selfie | YCbCr false-skin on clothes | MediaPipe skin coverage | Note |
|---|---|---|---|
| **selfie04** | **99.2 %** | 14.2 % | burgundy top — the documented false-flag; MP fixes it entirely |
| selfie02 | 85.9 % | 12.9 % | tan/warm outfit |
| selfie11 | 78.4 % | 1.7 % | beige |
| selfie01 | 65.5 % | 10.0 % | warm/orange top |
| selfie25 | 63.5 % | 3.4 % | warm neutral |
| selfie12 | 44.3 % | 13.8 % | light warm |

MediaPipe's `body-skin`/`face-skin` coverage on these stays low (just the real
exposed skin — face/arms), while the warm garments correctly land in `clothes`
(e.g. selfie04: clothes = 1.44 M px, the burgundy top clearly in-class, skin only
14 %). **This is a real, evidence-backed win:** a learned skin class cleanly
separates skin from warm-toned garments where the YCbCr heuristic catastrophically
fails, directly addressing the PRD §9 skin-bias risk. It also means the
segmentation *itself* can replace the skin heuristic, not just augment it.
