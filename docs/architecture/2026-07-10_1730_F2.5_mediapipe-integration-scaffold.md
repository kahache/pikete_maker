# F2.5 — MediaPipe garment-segmentation integration scaffold (Flutter)

Date: 2026-07-10 · Phase 2.5 · Author role: Mobile Dev
Status: **structural scaffold merged into `app/` — additive, zero regression.**
Follows the prototype spike (`2026-07-10_1700_F2.5_mediapipe-prototype.md`, GO
on MediaPipe Selfie Multiclass = D21) and its confirmed backend contract
`segment_garments(rgb) -> {"upper": mask, "lower": mask}`.

TL;DR: the app now has the on-device clothing-segmentation SEAM in place
(`lib/core/segmentation/`), wired into the color engine behind a default
whole-photo segmenter that is a **provable no-op**. No model, no native
dependency, no build change. `flutter analyze` = 0, `flutter test` = 71/71
(66 + 5). The real MediaPipe inference is a documented, loudly-failing STUB —
it needs an Android SDK/device this machine does not have.

## 1. Why now, and what this is NOT

The MVP extracts ONE palette from the whole photo (D1). The differentiator
(PRD, not-optional) is a palette PER GARMENT (top/bottom). The spike proved the
model works and retires the YCbCr skin proxy. But TFLite cannot run on this box
(no Android SDK/device, headless GL). So this deliverable is the **structural
scaffold + integration design**, not working inference. The bright line held:
the whole-photo MVP flow is byte-for-byte unchanged, and every test stays green.

## 2. Files added (all additive)

- `lib/core/segmentation/garment_segmenter.dart` — the seam. `GarmentSegmenter`
  interface (`segment(rgba, w, h) -> GarmentSegmentation`), `GarmentRegion`
  enum `{ whole, upper, lower }`, `GarmentSegmentation` (region → per-pixel 0/1
  `Uint8List` mask, mirroring the backend mask contract), and
  `SegmentationException`. Mirrors the doc/abstraction style of
  `color_engine.dart`.
- `lib/core/segmentation/whole_photo_segmenter.dart` — DEFAULT impl. Returns one
  `GarmentRegion.whole` mask with every pixel selected → reproduces today's
  behavior exactly.
- `lib/core/segmentation/mediapipe_garment_segmenter.dart` — STUB for the real
  impl. Documents the full plan and `throw`s `UnimplementedError` so it cannot
  ship pretending to segment.
- `lib/core/segmentation/segmented_result.dart` — additive result models
  `GarmentPalette` and `SegmentedAnalysisResult` (UNUSED by default; the MVP
  still returns `AnalysisResult` and the result screen is untouched).
- `test/core/segmentation/whole_photo_segmenter_test.dart`,
  `test/core/segmentation/mediapipe_garment_segmenter_test.dart` — synthetic
  buffers, no real model.

Wiring change (the only touch to existing code):
`ColorEngineDart({this.segmenter = const WholePhotoSegmenter()})` — a `const`
default arg, so every existing `const ColorEngineDart()` call site is
unaffected. In `_decodePixels`, at the point the RGBA buffer is produced, the
engine now asks the segmenter for the `whole` mask and passes it to
`extractRgbaPixels(rgba, mask: ...)`. `extractRgbaPixels` gained an optional
`{Uint8List? mask}`; a null/all-ones mask keeps ALL pixels → identical output.
A dedicated test asserts `extractRgbaPixels(rgba, mask: wholeMask) ==
extractRgbaPixels(rgba)`.

## 3. Decision — the Dart TFLite integration path

**Chosen: MediaPipe Tasks (Image Segmenter), NOT raw `tflite_flutter`.**

| Option | Pro | Con | Verdict |
|---|---|---|---|
| **MediaPipe Tasks** (`ImageSegmenter`) | Ships the model's 256×256 pre/post-processing (resize, normalize, per-class argmax) AND the Android GPU/CPU delegates. We feed pixels, get a class mask. Matches how the spike ran the model. | Newer Flutter plugin surface; adds native MediaPipe AARs → APK weight (watch G1/G2.5). | **CHOSEN** |
| `tflite_flutter` + manual pre/post | Minimal, well-known plugin. | We reimplement resize + normalize + argmax over 6 channels by hand, and pick our own delegate. More code to get wrong for no upside — the model is a MediaPipe artifact. | Documented fallback |
| Platform channel (write native Kotlin/Swift) | Full control. | Most work, two codebases, defeats "one Flutter codebase" (D4). | Rejected |

Rationale: the asset is a first-party MediaPipe model; its Tasks runtime owns
the exact pre/post it was trained against, so Tasks is the lowest-risk path to
reproduce the spike's numbers on-device. `tflite_flutter` stays the fallback if
the Tasks plugin proves immature on our min-SDK. **Neither dependency is added
yet** — that happens on a machine with the Android toolchain, in the same PR
that wires `MediaPipeGarmentSegmenter`.

## 4. Model-asset strategy (the 16 MB `.tflite` is NOT committed)

`selfie_multiclass_256x256.tflite` is 16.37 MB — it does **not** go in git.
Plan:
1. A `tool/fetch_models.dart` (or Gradle/CI step) downloads it from Google's
   published MediaPipe model URL into `app/assets/models/` (gitignored), pinned
   by SHA-256 for integrity/reproducibility.
2. `pubspec.yaml` declares `assets/models/` so Flutter bundles it into the APK.
   It ships INSIDE the app (D2/D21: 100% offline) — the download is a build-time
   fetch, never a runtime network call.
3. `MediaPipeGarmentSegmenter.modelAsset` already names the key
   (`assets/models/selfie_multiclass_256x256.tflite`) so the stub's error
   message is honest about what is missing.

APK-size note (G1/G2.5): +16 MB model + MediaPipe native libs is the real cost
to watch; measure on the first device build. D22 already makes segmentation
latency non-blocking (the ad/progress covers it).

## 5. Data flow: segmentation → per-garment palettes

The colorlab Dart port is reused UNCHANGED. Only the pixel selection changes:

```
bytes → decode+downscale → RGBA(w,h)
      → segmenter.segment(rgba,w,h)              # MVP: whole; MP: upper+lower
      → for each region R:
            extractRgbaPixels(rgba, mask: R)     # existing fn, now mask-aware
            → buildResult(pixels)  → AnalysisResult   # UNCHANGED pipeline
            → GarmentPalette.fromAnalysis(R, result)
      → SegmentedAnalysisResult([upper, lower])
```

The MediaPipe impl (per the spike): argmax the 6 class channels → `clothes`
(index 4) pixels = the garment mask; split at the mid-height of the clothes
bounding box → `upper` (row < mid) / `lower` (row ≥ mid); skin (`body-skin`/
`face-skin`) is simply excluded — no YCbCr box. Inference runs ONCE per frame
and returns both regions (the interface returns all masks in one call, so we
never pay for inference twice).

## 6. UI implication (out of scope now)

The result screen (`features/result/result_screen.dart`) is deliberately
untouched: the MVP still passes it a single `AnalysisResult`. When segmentation
ships, the screen grows per-garment sections ("Parte de arriba" / "Parte de
abajo"), each rendering a `GarmentPalette` (same palette/BASE/harmonies widgets,
just repeated per region). `SegmentedAnalysisResult` is the model it will
consume. That screen redesign is a separate UX + mobile task, gated by a
ux-designer spec — NOT part of this scaffold.

## 7. Phasing

- **v1 (D21):** MediaPipe Selfie Multiclass, top/bottom via the geometric
  bbox-midpoint split. No footwear. Ship this first.
- **v1.1:** refine the split with MediaPipe Pose hip-line landmarks (better for
  long coats / cropped tops). Logged, not blocking.
