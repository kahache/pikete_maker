# I2 waist guard — `hip_split_row` edge-minimum fix

Date: 2026-10-01 · Role: ml-engineer · Phase: F2 (I2 "Vérmelo puesto", follow-up
of the block Q fix pass) · Budget: M

Follows `2026-09-30_1830_F2_I2-mask-hardening-C1.md` §2 (hip split). Labels:
VERIFIED = run or looked at on this PC; HYPOTHESIS = reasoned, not run. Panels
are private (`outputs/i2-gate/waist-guard/`, gitignored) and referred to by
photo stem only. Fashionpedia eval photos are referred to by their numeric id
(`seg-fp-NN`).

## 1. The problem (VERIFIED)

`hip_split_row` takes the minimum of the smoothed clothes-width profile inside
`HIP_SEARCH_BAND = (0.30, 0.55)` of the clothes bbox height and calls it a
waist when it is strictly inside the band and narrower than
`HIP_WAIST_MAX_RATIO` (0.85) × the widest row on both sides. When the model
labels a raised sleeve "others" (reproduced here on the head-pixelated copy of
selfie24, see §3), the torso reads as a narrow, nearly flat band that widens
down to the hips; the argmin lands 2–4 rows inside the band's upper edge,
mid-shirt. The upper region then holds only 22–24 % of the clothes area and
the ABAJO recolor paints the lower half of the shirt together with the
trousers.

## 2. Candidates

All candidates live only in `hip_split_row`, i.e. only on the OPT-IN
hardening path (`split_garment_masks(harden=...)`, `RECOLOR_HARDENING`). The
canonical palette path never calls it.

| Variant | Rule added to the existing waist acceptance (any failure -> v1 mid-row) |
|---|---|
| A — band-edge guard | reject a minimum within one smoothing window of either band edge (`row - lo < window` or `hi - row < window`) |
| B — upper-share guard | reject a waist whose upper region (clothes pixels on rows `< row`) is `< 0.30` of the clothes area |
| C — A + B | both |
| E — valley bottom (explored) | move the argmin down to the last band row whose smoothed width is within +10 % of the minimum, then the usual checks |
| F — E + B (explored) | both |

The brief's refined edge variant (reject an edge minimum only when the inner
side is monotonic) was not built: on the failing stress map the profile does
dip on BOTH sides of the minimum (outer side ~47 px, minimum ~38 px, ratio
0.79 < 0.85), so a monotonicity test cannot tell it from a real waist; the
discriminating signal is how much garment ends up above the cut, which is B.

## 5. Verdict

**B adopted** (CEO criterion "if it complicates or hurts the algorithm, leave
it" is met: one comparison, zero changed decisions on the 65 real masks, the
reproduced failure fixed). A and C rejected: they lose two correct waists,
one of them a C1 VERIFIED one. E and F rejected: they move many decisions and
lose a VERIFIED waist.

Known limit (HYPOTHESIS, no such photo in the eval set): a cropped top over
long, wide bottoms can have a real waist whose upper share is below 0.30;
the guard would fall back to the mid-row and cut the bottoms. Same class of
failure as the existing waist-up limit; the v1.1 Pose hip line is the real
fix for both.

What B does not fix: the raised sleeve itself is still labelled "others" by
the model and stays out of ARRIBA (mask quality, not the split).

## 6. Rule spec for the Dart port (`hipSplitRow` in `app/lib/core/segmentation/mask_hardening.dart`)

New constant, same name style as the others:

```
const double kHipWaistMinUpperShare = 0.30;   // Python HIP_WAIST_MIN_UPPER_SHARE
```

In `hipSplitRow(clothes)`, AFTER the existing `HIP_WAIST_MAX_RATIO` check
and immediately before returning `(row, fromWaist: true)`:

```
upper = count of clothes pixels with y < row      // rows top .. row-1, all columns
total = count of clothes pixels in the whole mask
if (upper < kHipWaistMinUpperShare * total) return (mid, fromWaist: false);
```

- `clothes` is the same mask the function already receives (the hardened
  clothes plane); `mid = (top + bottom) ~/ 2` as today.
- Integer counts, comparison in double, strict `<` (a share exactly at 0.30
  passes).
- No other step changes; the order of the earlier rejections is irrelevant
  (they all return the mid-row).

Parity: `recolor_parity_I2.json` is byte-identical after the change (its
synthetic scenes never hit the guard), so the Dart port should mirror the
three new Python tests in `cv_core/tests/test_mask_hardening.py` (frame
320×240, silhouette rows start at y = 40, centred at x = 120, row i spans
columns `[120 - w//2, 120 + w//2)`):

| Test | Widths per row | Expected |
|---|---|---|
| edge minimum | `[50]*50 + [42]*5 + [38]*4 + [120]*121` | `(129, false)`; with the guard disabled `(95, true)`, upper share 0.156 |
| true waist near the guard | `[100]*55 + [60]*15 + [110]*110` | `(98, true)`, upper share 0.307 |
| fallback reaches the regions | edge-minimum silhouette + head classes, `split(harden: recolor, erodePx: 0)` | upper and lower regions contiguous, lower starts below row 110 |
