# F2.5 — MediaPipe Selfie Multiclass ON-DEVICE spike (real inference, measured)

Date: 2026-07-14 · Phase 2.5 · Author role: ML Engineer
Status: **spike DONE — real TFLite inference runs on-device behind the
`GarmentSegmenter` seam, measured on the `qa_e2e` emulator. MVP default
unchanged (WholePhotoSegmenter); outfit mode byte-identical.**
Follows the scaffold ADR (`2026-07-10_1730_F2.5_mediapipe-integration-scaffold.md`)
and executes its §8 "needs the Android toolchain" plan on the Windows dev PC
(toolchain installed 2026-07-11).

TL;DR: the 16.37 MB Apache-2.0 model **loads in 58 ms and segments a
721×1080 photo in ~233 ms** (emulator x86_64 CPU, 4 threads, full Dart
pre/post included). Masks on the one real-person photo available here are
**clean and correctly classed** (hoodie=upper, shorts=lower, skin/hair/face
right, sneakers land in "others", background people ignored), and a cartoon
person is **loudly rejected** (`isNoPerson`). Cost: **universal release APK
20.15 MiB → 47.45 MiB (+28.6 MB)** — mitigable to ~+19 MB per-ABI. The
runtime route had to be the ADR's documented fallback: **`tflite_flutter`**,
because the official MediaPipe Tasks VISION plugin does not exist on pub.dev.

## 1. Route chosen (one paragraph, per the spike brief)

The scaffold ADR preferred "MediaPipe Tasks (Image Segmenter)" with
`tflite_flutter` as documented fallback. Verified 2026-07-14 against the
pub.dev API: google/flutter-mediapipe publishes only `mediapipe_core`,
`mediapipe_text` and `mediapipe_genai` — **there is no official vision/
image-segmenter Flutter plugin**, and the third-party wrappers are unmaintained
one-offs. So the fallback is the route: **`tflite_flutter` 0.12.1** (TensorFlow
team, active, ships the Android `libtensorflowlite_jni.so` binaries), with the
model's pre/post-processing reimplemented in ~120 lines of pure Dart (bilinear
resize to 256×256 + [0,1] normalize → one `invoke()` → per-pixel argmax over 6
channels → clothes-bbox mid-row split). The [0,1] normalization and the class
map were validated empirically on the real photo (masks below are sensible;
wrong normalization produces garbage).

## 2. What landed (all additive; NO default-behavior change)

- `app/lib/core/segmentation/mediapipe_garment_segmenter.dart` — the stub
  replaced by the real implementation: `warmUp()` (explicit preload),
  `classify()` (full-res class map, diagnostic surface), `segment()` (the
  seam's contract → `upper`/`lower` masks), pure-static `preprocess`/
  `argmax`/`buildMasks` (host-testable). Every failure path (missing asset,
  missing native lib, bad buffer, no person) surfaces as the seam's typed
  `SegmentationException` — never garbage, never `UnimplementedError`.
- `app/pubspec.yaml` — `tflite_flutter: ^0.12.1` + `assets/models/` entry.
- `app/assets/models/` — the model lives here, **gitignored**
  (`app/assets/models/*.tflite` in `.gitignore`; a committed `.gitkeep`
  keeps the dir so fresh clones still build).
- `app/tool/fetch_models.sh` — reproducible build-time fetch, pinned:
  `selfie_multiclass_256x256.tflite`, 16 371 837 bytes, SHA-256
  `c6748b1253a99067ef71f7e26ca71096cd449baefa8f101900ea23016507e0e0`, from
  Google's MediaPipe model bucket. Build-time only — the app never touches
  the network (D2).
- `app/integration_test/segmentation_spike_test.dart` (+`spike_photos.dart`,
  base64-embedded fixtures: zero pubspec-asset/APK impact) — the on-device
  measurement harness that produced every number below. 3/3 passed.
- `app/test/core/segmentation/mediapipe_garment_segmenter_test.dart` —
  rewritten from "stub throws UnimplementedError" to real coverage of the
  pure-Dart pieces + the input-validation error path.

**Opt-in stays opt-in:** `ColorEngineDart`'s default is still
`const WholePhotoSegmenter()`; no production call site constructs
`MediaPipeGarmentSegmenter`. Outfit mode is byte-identical (the suite's
existing no-op-mask equality test still passes).

## 3. On-device numbers (emulator — read the caveat)

Device: AVD `qa_e2e` (Pixel 6 profile, android-35, **x86_64**, WHPX on the
i7-4790, headless swiftshader). CPU inference, 4 threads, no delegates.

| Metric | Value |
|---|---|
| Model load (rootBundle + interpreter) | **58 ms** |
| First inference (one-off allocations) | 288 ms |
| Steady inference ×10, 721×1080 photo | **mean 233 ms · median 226 · min 215 · max 303** |
| — includes | Dart bilinear resize + invoke + argmax + full-res upscale |
| RSS before load / after load / after runs | 284 MB / 320 MB (**+36 MB**) / 386 MB (incl. decoded photo + overlay buffers) |
| Budget (D2: < 3 s mid-range Android) | PASS with ~10× margin on this hardware |

**Caveat (binding number still pending):** this is an **x86_64 emulator on a
2014 Haswell**, not ARM. The Galaxy M33 was not on USB today. ARM NEON
performance on a mid-range phone is typically the same order of magnitude for
this model (the Python spike's laptop CPU did 430 ms), and D22 makes latency
non-blocking anyway — but the **formal gate-G2.5 number must be re-measured on
the M33** (one `flutter test integration_test/segmentation_spike_test.dart -d
<M33>` away). **RESOLVED later the same day — see the ADDENDUM at the end of

## 4. Mask quality (eyeball + numbers)

Only ONE real-person photo exists on this machine (`samples/selfies/` is
gitignored and absent; `samples/g0/raw/` not fetched). Used
`samples/vuitton2006lr.jpg` (runway, pink hoodie + pink shorts) + the
synthetic blocky person (`samples/test_outfit.png`) as a negative control.

**vuitton2006lr (721×1080)** — overlay:
`outputs/segmentation-spike/spike_vuitton_overlay.png` (gitignored dir;
regenerate by re-running the harness):

- Coverage: clothes **19.5%** · body-skin 2.9% · face-skin 1.1% · hair 0.3% ·
  background 74.5% · others 1.8%.
- **Verdict: clean.** The hoodie is fully `upper` (sleeves + drawstrings
  included), the shorts fully `lower`; the bbox mid-row split lands almost
  exactly at the hoodie hem. Legs/neck = body-skin, face = face-skin, hair =
  hair. **The sneakers land in "others"** (consistent with D21's no-footwear
  scope — the class exists if Phase 2S ever wants it, but it's "accessories",
  not a shoe detector). Blurred background people are NOT misattributed.
- Region palettes: upper mean `#D74085`, lower mean `#DC2F7F` — both pink,
  **correct** (it is a monochrome pink outfit); masks disjoint (0 shared px).
- Known imperfection: mask edges are slightly blocky (256→1080
  nearest-neighbor). For palette extraction this is minor (edge pixels are a
  small minority), but v1 should **erode masks a few px** before feeding the
  palette to avoid boundary color bleed.

**Synthetic cartoon person:** clothes 0.0% → `segment()` throws
`SegmentationException(isNoPerson: true)`. The loud-degrade path works
end-to-end on-device; the model does not hallucinate garments on non-photos.

Not covered here (needs the D23 eval set): diverse skin tones/lighting, real
no-person photos (the CEO's `dataset_zapas` photos are personal and must not
be embedded in committed fixtures), multi-person frames. The Python prototype
already validated the same artifact on the 31 real selfies (27/31 improved,
0 worse) — this spike's claim is **on-device parity**, not re-validation.

## 5. APK size (gate G1/G2.5 cares)

Universal release APK, Flutter 3.32.8 + JDK 17, measured before/after on a
clean HEAD worktree (so a concurrently-landing `url_launcher` change didn't
contaminate the delta; the "after" build is debug-signed — size-neutral):

| | bytes | MiB |
|---|---|---|
| Baseline (HEAD, r9-era) | 21 131 800 | 20.15 |
| + model + tflite_flutter | 49 756 446 | 47.45 |
| **Delta** | **+28 624 646** | **+27.3 MiB** |

Attribution (from the APK zip):
- Model asset: **+16.37 MB, stored UNCOMPRESSED** (Android keeps `.tflite`
  uncompressed so it can be mmap'd; float32 weights barely deflate anyway).
- TFLite JNI libs, compressed: arm64 **2.78 MB** (1.75 jni + 1.04 gpu) ·
  armeabi-v7a 2.34 MB · x86 3.68 MB · x86_64 3.45 MB ≈ **12.25 MB total**.

Mitigations for the real release (decide before beta ships this feature):
1. **`--split-per-abi` / app bundle** — an arm64 user pays ~+19.2 MB, not
   +28.6 MB. The F&F beta distributes a raw APK → split matters there too.
2. **Drop `libtensorflowlite_gpu_jni.so`** via gradle `packagingOptions` if we
   stay CPU-only (−~1 MB/ABI compressed). Or do the opposite: adopt the GPU
   delegate deliberately for the latency win. Don't ship it unused.
3. **fp16 model conversion** could halve the 16.37 MB; MediaPipe only
   publishes float32 for multiclass, so this is our conversion + re-eval work
   (quality check against the Python reference masks). Optional, later.

## 6. Build/toolchain notes (this PC)

- `tflite_flutter` wants **compileSdk 36**; the project pins 35 → today it
  builds with a loud warning. Fold `compileSdk = 36` into the pending
  Gradle/AGP upgrade chore (#79 territory); android-36 is already installed.
- Emulator run recipe = the #41 E2E recipe (JDK 17 + Flutter 3.32.8 +
  truststore env). The harness prints `SPIKE ...` lines with every number.
- Overlay retrieval: `adb exec-out run-as com.piketemaker.app cat
  code_cache/spike_vuitton_overlay.png > file.png` — **must be redirected by
  cmd.exe, not PowerShell** (PS redirection re-encodes and corrupts binary).
- Host `flutter test` cannot run inference (no `tensorflowlite_c` desktop
  lib in the Flutter cache) — expected; the failure path is typed. One host
  test of that path was dropped: tflite_flutter's lazy `DynamicLibrary`
  failure gets double-reported as an unhandled zone error under flutter_test
  regardless of assertion style (documented in the test file).
- Suite after the spike: **app 187/187 green, `flutter analyze` 0 issues**
  (3.44.6). `pubspec.lock` churned between 3.32.8 (this work) and 3.44.6 (a
  concurrent session) — whoever commits should sanity-check the lock.

## 7. What the FULL phase needs next (v1 = top/bottom, D21; no footwear)

1. **M33 measurement** (formal latency + memory on ARM; try XNNPACK/GPU
   delegate while at it). One command once the phone is on USB.
2. **Wire per-region palettes**: run the UNCHANGED colorlab port per region
   (`extractRgbaPixels(rgba, mask: upper/lower)` → two `AnalysisResult`s →
   `SegmentedAnalysisResult`), behind the same opt-in. Needs the result-screen
   per-garment UX spec (ux-designer) before any production wiring.
3. **Mask hygiene before palettes**: erode masks ~2–3 px (edge bleed, §4) and
   add a min-region-size guard (a 200-px `lower` region shouldn't emit a
   confident palette).
4. **D23 eval dataset** (30–50 own/commercial-safe photos, diverse skin tones
   / lighting / outfit types): run this exact on-device path over it and score
   masks per garment — that is the gate-G2.5 evidence, and where the PRD §9
   skin-bias risk is actually tested. The YCbCr proxy retirement (prototype
   §5) becomes real the moment the segmenter opt-in flips on.
5. **APK diet decision** (§5): split-per-abi/AAB + GPU-lib keep-or-drop —
   needs a CEO/PM call because it touches how the beta APK is distributed.
6. Known v1 limitations to carry: geometric mid-row split (v1.1 = Pose hip
   line), nearest-neighbor mask upscale, single "clothes" class (dresses/
   coats will straddle the split — the eval set must include them).

## ADDENDUM (2026-07-14, later the same day) — BINDING ARM measurement on the Galaxy M33

The §3 caveat is resolved: the same harness ran on the CEO's **Galaxy M33
(RFCTA1VDAPR, arm64-v8a, Exynos 1280)** over USB. Same build recipe (JDK 17 +
Flutter 3.32.8 + truststore `GRADLE_OPTS`), same config as the emulator run:
**CPU inference, 4 threads (tflite_flutter defaults, XNNPACK-enabled runtime),
no delegates** — this was a measurement run, not a delegate-tuning session.
All 3 harness tests passed.

| Metric | x86_64 emulator (§3) | **Galaxy M33 (ARM, binding)** |
|---|---|---|
| Model load (rootBundle + interpreter) | 58 ms | **184 ms** |
| First inference (warm-up) | 288 ms | **683 ms** |
| Steady inference ×10, 721×1080 photo | mean 233 · median 226 · min 215 · max 303 ms | **mean 555.7 · median 540 · min 460 · max 637 ms** |
| RSS before / after load / after runs | 284 / 320 / 386 MB | **259 / 294 (+35 MB) / 359 MB** |
| Coverage + region means (vuitton) | §4 values | **identical** (bg 74.5% · clothes 19.5% · upper `#D74085` · lower `#DC2F7F`) |
| Synthetic cartoon | rejected, `isNoPerson` | **rejected, `isNoPerson`** (same path) |

- **x86 vs ARM in one line:** the real mid-range phone is ~2.4× slower than
  the emulator-on-desktop but stays in the same order of magnitude, and the
  masks are numerically identical (same coverage, same region means) — the
  emulator remains a valid functional proxy; only latency numbers must come
  from ARM.
- **D22 / D2 verdict: the < 3 s mid-range budget HOLDS on the real device.**
  Worst observed inference = the 683 ms warm-up; steady max 637 ms; even
  load + warm-up + one steady inference ≈ 1.4 s end-to-end. Latency is a
  non-issue for v1; GPU/NNAPI delegate exploration stays optional (only if a
  later gate wants sub-200 ms), not needed for gate G2.5.
- Operational note: installing the debug harness over the signed r9 triggers
  the expected `INSTALL_FAILED_UPDATE_INCOMPATIBLE` → auto-uninstall (app
  data reset). After the run the signed r9 was reinstalled on the M33
  (`adb install` → Success, `pm list packages` verified). Anyone re-running
  this harness on the CEO's phone must do the same restore.
