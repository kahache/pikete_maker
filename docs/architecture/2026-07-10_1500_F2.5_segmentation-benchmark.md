>   **MediaPipe Selfie Multiclass is the confirmed v1 direction.** Footwear moves

> - **Latency is not a gating criterion** — the rewarded ad (F8) covers

## 1. Why this matters (context)

Committed decision #1: ML clothing segmentation is the **non-optional
differentiator** (Powsty does not do it). Committed decision #2 / D2: the MVP
must run **on-device** (TFLite/MediaPipe, ~0 marginal cost) — a model that only
runs on a server does **not** clear gate G2.5. PRD §7 Phase 2.5 criteria:
per-garment mask quality, model size, mobile latency, license. Gate G2.5:
correct per-garment colors on ≥ 80% of the eval set, **< 3 s on a mid-range
Android**.

On-device budget (from D2, restated as hard filter for this benchmark):
model **< ~30 MB**, latency **< 3 s** on mid-range Android, convertible to
TFLite/ONNX-mobile. Anything that fails all three is a *reference/quality
ceiling*, not a shippable candidate.

This spike does two things:
1. Proves the **value** of per-garment segmentation with a heavy proxy model
   (rembg `u2net_cloth_seg`) — measured on this machine (§4).
2. Surveys the realistic **on-device** candidates and ranks a prototyping
   order (§3, §5).

### Key structural insight

There are **two families**:
- **Coarse-but-native** (MediaPipe): tiny, fast, on-device today, Apache-2.0 —
  but "clothes" is a single region. Splitting top/bottom needs a heuristic.
- **Rich-but-heavy** (SegFormer-ATR, SCHP, cloth_seg U²-Net): true per-garment
  incl. footwear, but each needs quantization/fine-tuning to reach the budget,
  and licenses of the fashion training data need commercial verification.

No single candidate is simultaneously (a) on-device-native, (b) per-garment
with footwear, and (c) clean commercial license. That gap is the core F2.5
engineering problem, and it drives the decisions in §6.

## 3. Ranked recommendation — what to prototype first toward on-device

1. **MediaPipe Selfie Multiclass** (build first). It is the only candidate that
   is on-device-native, fast, and Apache-2.0 *today*. It also gives a real skin
   class → directly retires the YCbCr skin-bias risk (PRD §9). Add a **top vs
   bottom split** via MediaPipe Pose landmarks (hip line) or a vertical-band
   split of the clothes mask. Ship footwear as "not covered in v1" unless the
   CEO requires it.
2. **SegFormer-B0 clothes (ATR)** (benchmark in parallel). This is the quality
   ceiling that *includes footwear*. Concrete task: export to TFLite int8,
   measure size + latency on a representative Android. If B0-int8 lands
   < 30 MB and < 3 s, it becomes the preferred single-model solution and makes
   the MediaPipe heuristic unnecessary.
3. **cloth-segmentation U²-Netp fine-tune** (fallback bespoke path). Only if 1
   and 2 both fall short. Fine-tune the 4.7 MB U²-Netp on Fashionpedia for
   upper/lower/full. More work; owned weights sidestep the license caveat.
4. **SCHP = offline tool, not a candidate.** Use it (or the full cloth_seg net)
   to auto-label the 30–50 photo eval set, then hand-correct. Never shipped.
5. **SAM/MobileSAM = deprioritized** for the automatic pipeline (no class
   labels). Revisit only if we add an *interactive* "tap a garment" feature.

### Proof of concept — per-garment palettes ARE distinct

The whole point of F2.5: feed each garment region into the existing colorlab
palette extraction and get *different* colors per garment instead of one
whole-photo palette. Using `colorlab.palette.dominant_colors` +
`colorlab.harmony.pick_harmony_base` (unmodified, called not edited), on the
two samples with both regions present:

**g0-06-varias-personas** (the clear win):
- WHOLE-photo base `#A6A5A7` (a muddy mid-gray — an average of everything).
- UPPER base `#0C0C0E` (black top), palette `[#0C0C0E 0.94, #9090A0 0.06]`.
- LOWER base `#79889E` (**blue-grey jeans**), palette `[#1C232F 0.73, #79889E 0.27]`.
- → Upper base ≠ Lower base. Segmentation recovers **black top + blue jeans**;
  the whole-photo pipeline collapses both into one meaningless gray.

**g0-02-total-black** (correct on a hard case):
- WHOLE-photo base `#E6EAED` (near-white — background/collar, **wrong** for a
  black outfit; exactly the attribution failure class in the CV-debt notes).
- UPPER base `#35333B`, LOWER base `#33323A` — both the real dark garment.
- → Segmentation puts the base on the actual black suit instead of the
  background. Distinct hexes, same (correct) dark family.

**Conclusion of the PoC:** per-garment segmentation changes the answer, and
changes it in the right direction — it fixes the dominant "attribution" error
class (garment vs background) documented in the CV technical-debt notes, and it
delivers genuinely distinct top/bottom palettes. The differentiator is real.

## 6. Decisions needed from CEO/PM before proceeding

1. **Footwear in v1 — required or deferred?** This is the pivotal choice. PRD
   §7 says "top / bottom / footwear". If **footwear is required**, MediaPipe
   and cloth_seg are out and the path is SegFormer-ATR (quantized). If **top /
   bottom is enough for v1**, MediaPipe (on-device today, cleanest license) is
   the fastest path and footwear becomes a v2 item.
2. **License posture on fashion-trained weights.** rembg `u2net_cloth_seg` /
   cloth-segmentation weights derive from iMaterialist competition data —
   **commercial use of the weights is unverified**. MediaPipe (Apache-2.0) is
   clean; SegFormer-clothes is MIT-carded but its ATR training data needs a
   check. Decision: are we willing to ship weights with an unverified training-
   data license, or restrict to Apache/MIT-clean lineages?
3. **Eval-set licensing.** Fashionpedia images are a CC mix and 3/8 of our g0
   photos are NC/ND (per `samples/g0/MANIFEST.md`) → **not commercial-safe** for
   a public/for-profit eval set. To build the 30–50 photo diverse eval set
   (PRD §7, incl. dark skin tones for the §9 bias fix) we likely need to
   **shoot our own photos or use CC-BY/Unsplash only**. Green-light this as the
   next concrete deliverable?
4. **Green-light the prototype order in §3** (MediaPipe first + SegFormer-B0
   TFLite measurement in parallel), and confirm access to a representative
   mid-range Android for the real latency numbers that gate G2.5 actually
   requires.

## 7. Interface note (for backend-architect)

When a model is chosen, the integration into `colorlab` should expose a
segmentation stage that returns per-region pixel masks, which the *existing*
`dominant_colors` / `pick_harmony_base` consume unchanged (validated in §4).
Proposed signature to agree on:

```python
# colorlab/segmentation.py (proposed)
def segment_garments(rgb: np.ndarray) -> dict[str, np.ndarray]:
    """Return {'upper': bool_mask, 'lower': bool_mask, ['footwear': ...]}.
    Masks are HxW boolean, aligned to rgb. Empty regions omitted."""
```

The palette pipeline then runs once per returned region. No change to
`palette.py` / `harmony.py` is needed — the PoC already drives them per-region.
