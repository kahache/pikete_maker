# F2.5 — Per-garment vs whole-photo on the 31 CEO selfies

Date: 2026-07-10 · Phase 2.5 · Author role: ML Engineer
Status: **working reference pipeline + quantified before/after** on the real MVP
dataset (`samples/selfies/*.jpeg`, 31 mirror selfies, neutral outfits). This is
the canonical Python reference the Dart MediaPipe impl will mirror.

## Headline

**Per-garment analysis improves the delivered color on 27 / 31 selfies**
(16 by splitting one blob into two distinct garment colors, 11 by isolating the
real garment from a background/skin-polluted whole-photo base). **0 regressions**
by the color metric. The remaining 4 are "same" — 2 genuinely single-color
outfits where whole-photo was already right, and 2 (selfie01, selfie04) where the
color matches but whole-photo would still fail *for a different reason* (the
YCbCr skin filter — see §4). One case (selfie10) is a **flagged ambiguity**, not
a confident win.

## Pipeline (per selfie)

1. MediaPipe Selfie Multiclass → `clothes` class → top/bottom split at the
   **mid-height of the clothes bounding box** (pure geometry, no Pose — same
   heuristic as the prototype).
2. Each region's pixels → colorlab **unmodified** (`dominant_colors` →
   `pick_harmony_base_index` / `pick_harmony_base`), giving a base + palette for
   UPPER and LOWER.
3. Whole-photo colorlab result on the full image, for comparison.

## Method — how "improved / same / worse" is decided (honest, mechanical)

No human ground-truth labels here: this measures whether **segmentation delivers
a more garment-faithful color than whole-photo**, by two CIELAB distances:

- `dE_ul` = deltaE(upper base, lower base) — how distinct top vs bottom are.
- `dE_wr` = min deltaE(whole base, region base) — how far the closest garment
  base is from the single whole-photo answer.

Buckets (threshold dE = 10, a deliberately conservative "visibly different"):
- **improved_split** — `dE_ul ≥ 10`: two distinct garment colors a single
  whole-photo palette cannot express.
- **improved_attribution** — `dE_ul < 10` but `dE_wr ≥ 10`: monochrome outfit,
  yet the garment base is far from the whole-photo base → segmentation isolated
  the real garment from a polluted whole base (light wall / background / skin
  average).
- **same** — `dE_ul < 10` and `dE_wr < 10`: whole-photo already equalled the
  garment; nothing to fix.
- **worse** — a garment region came back empty (split/segmentation failed).

Caveats stated up front: (a) the dE=10 threshold is a judgment call — borderline
rows (selfie11 dE_wr 10.9, selfie17 dE_wr 10.2, selfie25 dE_ul 10.4) sit on the
line; (b) the split is geometric, so a misplaced waistline can mis-assign a band;
(c) this is whole-vs-segmented, not vs CEO truth — the CEO should eyeball the
panels in `outputs/per-garment-selfies/` to confirm the qualitative calls.

## Whole-photo failure categories (why whole-photo is wrong)

Of 31 selfies, the whole-photo colorlab base falls into:
- **skin (6)** — base sits in the YCbCr skin box → the current app's `BASE_IS_SKIN`
  flag would mark it KO (this is the documented selfie04 bug class, PRD §9).
- **canvas (22)** — base is a strong neutral / near-black → whole-photo returns
  one muddy averaged neutral (top + bottom + skin + background collapsed).
- **chromatic (3)** — whole-photo did pick a chromatic base (may be from one
  garment only, or a small accent).

## 4. The skin cases (selfie01, selfie04) — the metric under-counts here

selfie04 is the canonical bug the coordinator cited (burgundy top read as skin).
It shows as **"same"** because whole-photo *did* extract the burgundy
(`#44181E` ≈ region `#3E151C`). The whole-photo failure is not the color — it is
that `#44181E` lands in the YCbCr skin box, so the current app's `BASE_IS_SKIN`
flag marks the result KO. Segmentation takes the burgundy from the `clothes`
class, so **no skin filter is applied and the color is kept by construction**
(from the prototype run: YCbCr would mis-flag **99.2 %** of selfie04's top as
skin). Same story for selfie01 (warm camel top, `#AF712C` in the skin box). So
the practical win is really **29 / 31**; I keep the headline at the stricter
color-metric **27 / 31** to avoid inflating, and flag these two explicitly.

## 5. Honest failures / ambiguities

- **selfie10 (⚠️ ambiguous, possibly a regression):** whole-photo picked a bright
  red `#A00E0F`; both segmented regions are dark maroon (`#451F34`/`#3C1E33`,
  dE_wr 59.5). Either whole-photo latched onto a small saturated red accent and
  segmentation gives the true dark garment (improvement), **or** there is a real
  red garment that the mid-height split + region averaging darkened (regression).
  The color metric cannot tell — **CEO visual check required.** Counted as
  improved in the table but should be treated as unresolved.
- **Geometric split is the weak link.** selfie08 (dE_wr 1.3: whole already matched
  the upper) and any garment with uneven proportions (long coat, cropped top) can
  have the waistline misplaced by the bbox-midpoint rule. No region came back
  empty on these 31 (worse = 0), but the split *assignment* is unverified without
  labels. **v1.1: replace midpoint with MediaPipe Pose hip landmarks.**
- **No ground truth.** These verdicts compare whole-vs-segmented, not vs CEO
  labels. The 31 review panels exist precisely so the CEO can confirm.

  `scratchpad/per_garment_compare.py`. Uses the isolated mediapipe (installed via

  ```bash

  env -u PYTHONPATH -u PIP_PREFIX -u PIP_BREAK_SYSTEM_PACKAGES \
    LD_LIBRARY_PATH="$SCR/stublibs" PYTHONPATH="$SCR/mp-libs:cv_core/src" \
    .venv/bin/python "$SCR/per_garment_compare.py"
  ```
