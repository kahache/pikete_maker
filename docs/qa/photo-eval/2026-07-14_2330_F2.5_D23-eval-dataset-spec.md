# F2.5 / D23 — Gate G2.5 evaluation dataset: spec + annotation guide

**Date:** 2026-07-14 23:30 · **Role:** QA · **Phase:** 2.5 (ML clothing
segmentation) · **Status:** SPEC — the dataset does not exist yet; this
document tells the CEO exactly what to shoot/source, and the harness
(`cv_core/tools/segmentation_battery.py`) is ready to consume it.

**What this dataset decides:**

1. **Gate G2.5** (PRD §7): *correct per-garment colors on ≥ 80% of the
   evaluation set, with latency < 3 s on a mid-range Android.* This set is the
   "evaluation set" of that sentence. (The latency leg is already measured
   separately on the Galaxy M33 — see §7.)
2. **The PRD §9 skin-tone bias test** (risk: "Skin filter bias (dark skin
   tones) — High reputational impact"; precedent: bug B1 / the selfie04
   burgundy-read-as-skin case). D23 green-lit an *own, commercial-safe* set
   with diverse skin tones precisely because Fashionpedia is CC-mixed and the
   31 CEO selfies are a single-person, single-skin-tone sample. **A gate that
   passes overall but fails a skin-tone bucket is a FAIL** — the harness
   encodes this (§6).

Per the on-device spike
(`docs/architecture/2026-07-14_2235_F2.5_mediapipe-ondevice-spike.md`), masks
are numerically identical between the x86_64 emulator and the ARM Galaxy M33,
so **the emulator is a valid functional proxy for mask generation**; only
latency numbers must come from the phone (they already do — addendum).

---

## 1. Size and the skin-tone axis (the mandatory one)

**Target: 36–48 photos. Hard floor: 30.** Fewer than 30 and the per-bucket
bias table stops meaning anything.

Skin-tone buckets (coarse on purpose — three buckets a non-specialist can
assign consistently; based on Monk Skin Tone scale ranges):

| Bucket (manifest value) | Monk scale | Fitzpatrick (rough) | **Minimum photos** | Target |
|---|---|---|---|---|
| `light`  | MST 1–3  | I–II   | **10** | 12–16 |
| `medium` | MST 4–7  | III–IV | **10** | 12–16 |
| `dark`   | MST 8–10 | V–VI   | **10** | 12–16 |

- The **minimum of 10 per bucket** is pinned in the harness
  (`MIN_BUCKET_N = 10`): a bucket below 10 makes the bias test
  **underpowered** and the gate verdict can be at best UNDECIDED, never PASS.
- At the 80% bar, a 10-photo bucket needs **≥ 8/10** and a 12-photo bucket
  **≥ 10/12**. Honest statistical note: with n≈10–12 per bucket this test
  detects **large** gaps (e.g. 90% light vs 50% dark), not subtle ones. That
  is acceptable for v1 — B1 was a *large* failure mode (whole burgundy top
  eaten as skin) — but do not over-read a 1-photo bucket difference; the gate
  rule is the hard per-bucket bar, not a significance test.
- **Every photo must have exactly one bucket assigned in the manifest.**
  Unbucketed photos block a PASS (the bias table would be incomplete).
- Bucket assignment is done by the annotator (CEO) at manifest time, from the
  photo. Borderline case → pick the bucket that keeps the counts most
  balanced and note it in `notes`.

**Anti-confound rule (important):** the hard cases below must be **spread
across buckets**, not concentrated in one. Each bucket must contain at least:
**2 dress/one-piece photos, 2 busy-background photos, 2 non-ideal-lighting
photos**. Otherwise a bucket could fail because it got all the dresses, and
the bias table would confound skin tone with photo difficulty.

## 2. Diversity matrix (marginal quotas over the whole set)

One photo covers several axes at once; these are minimum counts over the full
set (36–48), not a factorial design.

| Axis | Value | Min | Why |
|---|---|---|---|
| **Garments** | distinct-color top + bottom | 15 | the core per-garment promise (split must deliver 2 colors) |
| | monochrome / all-neutral outfit | 6 (≥ 3 total-black) | canvas-mode (D10) interaction; whole-photo already handled these — segmentation must not regress them |
| | **dress / one-piece** | 6 | **known hard case (D21/spike §7.6):** single `clothes` blob straddles the geometric mid-split — both regions must still read as the dress color |
| | long coat / oversized top | 3 | misplaces the bbox mid-row (waistline) — split-assignment stress |
| | small high-chroma accent on neutral outfit | 3 | the #57/D20 residual explicitly deferred to Phase 2.5 |
| **Background** | plain wall / door (D11 tutorial happy path) | 20 | the instructed use case |
| | busy (room clutter, street, patterned) | 10 | the #56 background-attribution bucket segmentation must fix |
| | mirror visible (frame, edge reflections, smudges) | 6 | mirror-selfie is the MVP framing; mirrors add ghosting |
| **Lighting** | good / diffuse | 24 | baseline |
| | backlight (window/light source behind) | 5 | classic segmentation killer |
| | dim / warm indoor (yellow cast) | 5 | color-cast stresses "correct color" judgment too |
| **Framing** | mirror selfie, full body (phone visible) | 20 | primary MVP use case (D23 explicitly requires it) |
| | full body shot by another person | 8 | beta users will also do this |
| | waist-up / lower body cut off | 5 | exercises the "garment out of frame → n/a" annotation path and the empty-lower-region guard |

Sanity check: the quotas are satisfiable inside 36–48 photos (they overlap;
e.g. one photo can be `dark` + dress + busy bg + mirror selfie).

## 3. Sourcing rules (D23: commercial-safe ONLY)

Two sources, both mandatory (own photos alone won't reach 10 per bucket):

1. **Own shoot** (§4): CEO + friends & family volunteers. Target 15–25 photos.
   Zero licensing questions; real MVP conditions (real mirrors, real homes).
2. **Stock** (§5): **Pexels and Unsplash only** (their licenses permit
   commercial use), or explicit **CC0**. Target 15–25 photos — this is where
   the `dark` and `medium` bucket depth realistically comes from.

Hard rules (repeat of the G0 lesson — its manifest carries 3 NC/ND photos
flagged as a public-repo risk):

- **NO CC BY-NC, NO CC BY-ND, no "editorial use only"**, no Fashionpedia.
- Plain **CC BY** is acceptable only with author + URL recorded for
  attribution; prefer Pexels/Unsplash/CC0 to keep it simple.
- Every photo gets a row in `samples/segmentation/MANIFEST.csv` **before** it
  enters the set (schema in §6.1). No manifest row → the harness treats the
  photo as unbucketed → blocks PASS. This is deliberate.
- **Privacy (own photos):** photos of friends/family are personal data. Same
  policy as `samples/selfies/`: the raw photos are **gitignored**
  (`samples/segmentation/photos/`), never committed, and each identifiable
  person gives explicit OK for internal QA use (a WhatsApp "sí" is fine —
  keep it). The committed manifest stores no names (author = "own").

## 4. CEO shot-list (own-photo session — mirror of the sneaker session, but for outfits)

Recruit **3–6 people** (F&F beta volunteers are the natural pool) aiming to
cover all three skin buckets in person if possible. Per person, 3–5 photos
from this menu (~10 min/person):

1. **Baseline:** mirror selfie, full body, plain wall behind, daylight,
   distinct-color top + bottom (e.g. red top / blue jeans). — 1 per person.
2. **Neutral:** same framing, all-black or all-neutral outfit. — at least 3
   people total.
3. **Dress / one-piece** (or long coat if no dress available). — at least 2
   people total, ideally across different buckets.
4. **Busy background:** same outfit as (1), but kitchen/room clutter or
   street behind. — at least 3 people total.
5. **Bad light:** one backlit (window behind) and/or one warm dim indoor
   shot. — at least 4 photos total.
6. **Waist-up:** one deliberately cropped shot (lower body out of frame). —
   at least 3 photos total.

Practical rules (same discipline as the sneaker session):
- Phone camera, default settings, **no filters/beauty mode** (they shift
  colors — the ground truth is the color as shot).
- Portrait orientation, subject roughly centered, whole outfit in frame
  (except the deliberate waist-up shots).
- After each shot, note the outfit's true colors while in front of the person
  ("top: rojo teja, bottom: vaquero azul") — this becomes the
  `expected_top`/`expected_bottom` manifest columns and is the
  anti-anchoring pre-registration (§6.2).
- File naming: `seg-NN-slug.jpg` (e.g. `seg-07-dress-busybg.jpg`),
  sequential, lowercase.

## 5. Stock part — downloader

Keep it manifest-driven (same idempotent spirit as
`cv_core/tools/download_battery_dataset.sh`): curation is manual (a human
must judge skin bucket, garments and license anyway), the *download* is
scripted so a fresh machine can rebuild the gitignored set.

1. Curate candidates on pexels.com / unsplash.com. Useful queries: "outfit
   mirror selfie", "full body outfit", "black woman fashion full body",
   "dark skin street style", "dress full length", "ootd". Check each photo
   against the matrix gaps (the harness's `--coverage` planning aid, §6.4,
   prints which cells are still short).
2. For each keeper, add its manifest row FIRST (with the **direct image URL**
   in `url`, plus author/license/skin/axes/expected colors).
3. Fetch everything missing (idempotent — skips files already present):

```bash
# from the repo root (Git Bash); reads MANIFEST.csv, downloads url -> photos/<file>
cd samples/segmentation
tail -n +2 MANIFEST.csv | while IFS=, read -r file source url rest; do
  [ -n "$url" ] && [ ! -f "photos/$file" ] && curl -L --fail -o "photos/$file" "$url"
done
```

(If this grows hairy — commas inside fields, auth — promote it to a proper
`cv_core/tools/download_eval_dataset.py`; not worth it until it hurts.)

Unsplash/Pexels direct URLs can rot; that's acceptable — the photos live on
the CEO's machines like the selfies do, and the manifest documents
provenance/license, which is the part that must survive.

## 6. Annotation guide + harness contract

### 6.1 The manifest — `samples/segmentation/MANIFEST.csv` (committed)

One row per photo. Header (exact, parsed by the harness):

```csv
file,source,url,author,license,skin,garments,background,lighting,framing,expected_top,expected_bottom,notes
seg-01-baseline.jpg,own,,,own,medium,top_bottom,plain,good,mirror_selfie,"rojo teja","vaquero azul",
seg-02-dress.jpg,pexels,https://...,Jane Doe,Pexels,dark,dress,busy,good,other_full,"vestido amarillo","vestido amarillo",
```

Allowed values — `skin`: `light|medium|dark` · `garments`:
`top_bottom|mono|dress|coat|accent` · `background`: `plain|busy|mirror` ·
`lighting`: `good|backlight|dim` · `framing`:
`mirror_selfie|other_full|waist_up`. Free text in
`expected_top`/`expected_bottom`/`notes`.

### 6.2 Ground truth = pre-registered color words + 2 verdict columns

**What the human annotates and why (the cheap-annotation decision):**

- **Before running the harness** (ideally at shoot/curation time), write the
  garments' true colors **in words** in `expected_top`/`expected_bottom`.
  Words, not hexes: an eyedropper hex would cost minutes per photo and false
  precision (which pixel of a shaded sleeve is "the" hex?). The words are the
  pre-registration that stops the reviewer from anchoring on whatever the
  pipeline output shows ("well, I guess it *is* sort of teal…").
- **After the harness run**, the CEO fills exactly **two verdict columns** in
  the generated `review.md` (same mechanic as the G2S product battery, which
  the CEO has already done once):
  - **`top color OK?`** — does the UPPER region's highlighted BASE swatch
    honestly read as the color you pre-registered for the top garment?
  - **`bottom color OK?`** — same for the LOWER region / bottom garment.
  - Tokens: `yes`/`no` (also `si`, `ok`, `ko`…), plus **`n/a`** when that
    garment is legitimately not in frame (waist-up shot → `bottom = n/a`).
    Anything else stays `pending` and never counts toward the gate.

This maps 1:1 onto the gate sentence ("correct per-garment colors"): a row
**passes** when every applicable column is `yes`. Rejected alternatives:
per-pixel mask IoU labels (hours of polygon work, and G2.5 is about delivered
*colors*, not mask pixels) and hex ground truth (cost + false precision, above).

Edge rules for the reviewer:
- **Dress/one-piece:** both regions should show the dress color → judge both
  columns against the dress. If the split leaks (e.g. lower region reads as
  the background), that column is `no` — that's the hard case working as
  intended.
- **Region came back EMPTY** (hint `EMPTY_UPPER`/`EMPTY_LOWER`): if the
  garment IS visible in the photo → `no` (segmentation missed it). If it's
  genuinely out of frame → `n/a`.
- **`NO_PERSON` hint** on an eval photo (they all contain a dressed person):
  auto-prefilled `no`/`no` — a wrongful rejection is a hard fail.
- **Judge the snap-displayed swatch** (the `#85` D31-A neutral snap is shown,
  raw hex kept as annotation) — the user sees the snapped color.
- Multiple people in frame: judge the centered/main subject.
- Color-cast photos (dim/warm): judge against what the garment *looks like in
  that photo* — the pipeline can't un-cast what the camera saw.

### 6.3 Mask handoff format (mask producer → harness)

*(Updated 2026-07-15, same kit-build session: the ML engineer landed
`colorlab.segmentation` + `cv_core/tools/generate_masks.py` in parallel; the
contract below is that shared one, and the harness consumes the canonical
layer instead of replicating the split.)*

- For each `photos/<stem>.<ext>` there is a **`masks/<stem>.mask.png`**:
  single-channel **grayscale mode-'L'** 8-bit PNG, **pixel value = raw class
  index 0–5** (0 bg · 1 hair · 2 body-skin · 3 face-skin · 4 clothes ·
  5 others — the MediaPipe Selfie Multiclass indices). It looks near-black
  in a viewer; that's expected (values ≤ 5). The contract is defined by
  `colorlab.segmentation.save_class_mask` / `load_class_mask`, which
  validates loudly (a colored/scaled PNG fails, never silently misreads —
  the harness turns it into a CRASH auto-fail row).
- **Bulk producer:** `python cv_core/tools/generate_masks.py photos/*.jpg
  -o masks/` — real inference via `ai-edge-litert` (the one TFLite runtime
  with a Py3.14/Windows wheel; `pip install -e "cv_core[seg]"` + `bash
  app/tool/fetch_models.sh` once per machine), through the canonical
  Dart-parity pre/post-processing, so masks are byte-compatible with
  on-device ones.
- **Parity spot-check (QA, before signing the gate):** regenerate a handful
  of masks via the on-device/emulator path (the spike harness pattern in
  `app/integration_test/segmentation_spike_test.dart`; pull with
  `adb exec-out ... cat` under cmd.exe redirection, spike §6) and diff them
  against the generate_masks.py ones. The spike already proved emulator ≡
  device; this closes Python ≡ device on real eval photos.
- If a mask comes at a different resolution than the photo (on-device decode
  caps the long side at 1080), the harness resizes its photo copy down to
  the mask's dimensions (bilinear) so pixels align.
- The upper/lower split + mask hygiene (2 px erosion, min-region guard,
  `NoPersonError`) are **consumed unmodified from
  `colorlab.segmentation.split_garment_masks`** — the harness scores exactly
  what the engine delivers, by construction. If the split evolves (v1.1 Pose
  hip line), the harness follows automatically.

### 6.4 Harness commands

```powershell
# from the repo root, project venv
# 0) generate the class masks (once per dataset change; needs cv_core[seg])
.venv\Scripts\python.exe cv_core\tools\generate_masks.py `
    (Get-ChildItem samples\segmentation\photos\*) -o samples\segmentation\masks

# 1) run the battery (photos + contract masks)
.venv\Scripts\python.exe cv_core\tools\segmentation_battery.py `
    --dir samples\segmentation\photos --masks samples\segmentation\masks

# planning aid while assembling the dataset (no masks needed):
.venv\Scripts\python.exe cv_core\tools\segmentation_battery.py --coverage

# 2) CEO annotates outputs\segmentation-battery\segmentation\review.md
# 3) gate verdict (overall + per-skin-bucket bias table)
.venv\Scripts\python.exe cv_core\tools\segmentation_battery.py --score
```

Outputs (per-dataset dir, gitignored): `results.json`, `<id>_panel.png`
(photo + class overlay + upper/lower palettes + expected words),
`index.html` gallery, `review.md` (the gate artifact).

## 7. Gate arithmetic (what --score enforces)

- `GATE_G25_MIN = 0.80` (PRD gate G2.5, pinned in the harness + a test).
- Row: pass = all applicable columns `yes`; fail = any `no`; `n/a` columns
  don't count; both-`n/a` rows are excluded loudly (mis-annotation smell).
- **Overall** pass-rate ≥ 80% **AND every skin bucket independently ≥ 80%**
  (each with n ≥ `MIN_BUCKET_N = 10`). Bucket short of 10 → bias test
  underpowered → verdict capped at UNDECIDED. Any unbucketed row → capped at
  UNDECIDED. Overall PASS + one bucket FAIL → **FAIL** (the §9 rule).
- Partially-annotated reviews get the same worst/best bracket logic as the
  G2S battery (a pending row can never silently help).
- **Latency leg:** not measured by this harness. Evidence = the spike
  addendum's Galaxy M33 numbers (steady mean 555.7 ms, worst warm-up 683 ms,
  < 3 s with margin;
  `docs/architecture/2026-07-14_2235_F2.5_mediapipe-ondevice-spike.md`).
  Re-confirm on the M33 with the final wired engine before signing the gate.
